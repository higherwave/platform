Evidence-based Patterns to Add to Our MCP Library
Research Insights
  1. Better session context needed: around the stream - device, network, etc.?
  2. Cognitive Overload: The UI is unnecessarily loaded with an overwhelming number of static options and text.
  3. Data retention policies hindered investigation follow-ups
  4. Every group had common investigations that were a repetitive bottleneck.
  5. Time-wasted in context-switching
What was done
  1. New IA, that supported scale without disorienting power users.
  2. Reduced cognitive overhead (new layouts using new DS components)
  3. Prompt library added for automating repetitive Netflix stream investigations.
  4. Preparation for the next step: deeper dives on content strategy (deprecating unused logs, simplifying those that stay, and adding AI prompt/response telemetry).
What outcomes were achieved
  1. Simplified workflows by improving usability, consistency, and scalability - paving the way for automated investigations and faster insights.
  2. Achieved the redesign and mapped common workflows with no disruption to existing users.
  3. Pilot project (eventually pushing to production) of a new design-to-code pipeline.

End-to-End Process that Starts Small and Scales to Multi-App Platform (especially when combined with the Design to Code MCP pipeline)
Process
Time scales can range from a few weeks (with little user feedback) to a quarterly release (with deeper and more grounded user research)
01
Context and Understanding
  1. Tribal knowledge first (CSMs/pre-sales, Support, etc.)
  2. Relevant telemetry data or KPIs
  3. Direct Customer Feedback
    1. Short Test Plan and Task list (questions to ask, personas, expected outcomes)
    2. Capture feedback with transcriptions and video.
    3. Summarize and prioritize themes with AI
    4. Journey maps (and/or user flows) for team clarity
START SMALL
A handful of CSM/Support conversations and the KPIs you already have.
SCALE AS NEEDED
Recurring customer interviews, a shared research repository, and AI-synthesized themes across personas.
→
02
Design Integration (with scale in mind)
  1. Integrate knowledge of the expected outcomes (JTBD), pain points, and how the design will scale.
  2. Evaluate the need to apply the most common usability principles:
    1. Confusing navigation
    2. Cognitive overhead with content and options
    3. Relevant content and proper terminology/labeling used
    4. Affordance and discoverability
    5. Consider where AI will integrate, applying deterministic data, and where humans will be in the loop
    6. Consider onboarding and change management
START SMALL
Fix the top usability issue in one high-traffic workflow.
SCALE AS NEEDED
Roll proven patterns into DS components and define shared AI and human-in-the-loop patterns across products.
→
03
Prototyping and Testing with Design-to-Code Pipeline (test on the real UI, not a simulation)
  1. Review internally and address questions/concerns on approach
  2. Put in front of customers (preferably contextual inquiry)
START SMALL
One prototype on the pipeline, reviewed internally and with 2–3 users.
SCALE AS NEEDED
The pipeline wired into every repo, with contextual inquiry on each release.
→
04
Release and Measure
  1. Beta or Early adopter feedback
  2. Adoption, Engagement (preferably Time-to-value and retention)
  3. Continue to track usage (preferably AI assistant interactions and prompts/responses)
START SMALL
A small beta group and a basic adoption metric.
SCALE AS NEEDED
Dashboards for time-to-value, retention, and AI prompt/response telemetry.

PIPELINE ARCHITECTURE
A Deterministic Build-and-Lint Pipeline for Design to Code
Four stages, one linter, zero manual design review.

A page spec is authored — sketch, Figma, or prose
→
Codegen

→

→

01 / 08
SYSTEM OVERVIEW
A lint gate sits between generation and deploy
Rather than a person reviewing every diff for design-system compliance, an automated linter runs against every generated page before it can merge — the same enforcement model as a CI type-checker, scoped to tokens and components instead of types.
Design spec
A page spec, hand-drawn or in Claude Design
Codegen
Claude turns the spec into working markup and components
Token lint
Static analysis checks every color, component, and spacing value against schema
Deploy
A clean pass merges and ships automatically
A failed lint blocks the merge, the same way a failing test would.
02 / 08
STAGE 1 OF 4
We standardized on an existing token system instead of building our own
Every design-token contract needs a schema — approved colors, a spacing scale, a component API, a type ramp. Rather than define one from scratch, we adopted Carbon, IBM's open design system: versioned, documented, and already shipped in production for years.
Color tokens
Approved values, scoped to where each one is allowed to render
Spacing scale
A fixed 4px-base scale, not arbitrary pixel values
Component API
Buttons, inputs, and cards with a defined props contract
Type ramp
A fixed set of font sizes, weights, and roles
Same rulebook a designer already trusts — expressed as a schema a linter can parse.
03 / 08
STAGE 2 OF 4
The linter runs as a service Claude calls before every build
It's a static-analysis service, not a person in the loop — it holds the full token and component schema, plus a corpus of pages we've already built and approved, so new generations can be checked against precedent, not just rules.
The Linter
A static-analysis service Claude Code calls before — and after — generating a page
✓
Full token + component schema
Colors, spacing, components, and type, in one machine-readable contract
✓
A reference corpus of approved builds
Prior pages that passed, used as concrete precedent, not just abstract rules
✓
Wired into every future repo by default
Not a one-off audit — it's registered as a standing part of the build
04 / 08
STAGE 3 OF 4
Every diff is linted before it can ship
Before a page merges, the linter checks it against a fixed rule set — token drift, unapproved components, baseline accessibility. A failure returns the exact file and line, so it's fixed in the same pass instead of shipping off-spec.
✕ LINT FAIL
background: #3457d5;

<button>Continue</button>
A hardcoded hex value, and a plain button instead of the standard component
✓ LINT PASS
background: var(--cds-background);

<Button kind="primary">Continue</Button>
A token reference, and the standard Carbon button component
Deterministic rules, not a style opinion — same input, same verdict, every run.
05 / 08
STAGE 4 OF 4
We validated the linter against a legacy codebase it had never seen
To rule out overfitting, we pointed it at a production app built before the schema existed, with no seed data pointing to where problems were. It flagged real, specific violations everywhere they appeared.
0

Exactly what we'd expect from code predating the schema — confirming the linter catches real drift, not staged violations.
Hardcoded hex values
In place of token references — found in every file
Hand-rolled buttons and inputs
In place of the standard component imports
The app is being left as-is for now — this was a validation pass, not a refactor request.
06 / 08
ROLLOUT STATUS
The lint gate is now wired into every repo going forward
It's a standing check, not a one-time audit — every new page runs through it by default. Pages ship faster, stay on-schema automatically, and nothing off-spec merges without being flagged first.

07 / 08
WHAT'S NEXT
Harness engineering can wrap the rest of the agent's work in the same rigor
Our lint gate enforces one contract: design tokens and components. Harness engineering is the broader discipline of designing the scaffolding around a coding agent — tools, verification loops, memory, guardrails, and observability — so the whole build, not just the design layer, is reliable by construction rather than by review.
Tool orchestration
Defined file, terminal, and repo access instead of an unscoped agent
Verification loops
The agent tests and checks its own output before handing it off — our lint step is one instance of this
Context & memory
Persistent project knowledge, so the agent doesn't relearn the codebase each session
Guardrails
Hard constraints on what the agent can change, and permission gates on risky actions
Observability
Traceable logs of what the agent did and why, for every merged change
Our linter is one guardrail. Harness engineering is the discipline that builds the other four.
